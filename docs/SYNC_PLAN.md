Public web config and the trip ID are not access-control secrets. Authorized domains do not restrict Firestore to two people. Schema bounds reject oversized/malformed wire documents, but cannot stop an authenticated visitor making valid unwanted edits or exhausting Spark quota. Continue keeping portable backups.

## Firestore shape and validation

One document per place at `/trips/{tripId}/items/{localPlaceId}`; the ID matches the local catalog ID. Shared state lives at `/trips/{tripId}/state/roster` and `/trips/{tripId}/state/planner`. The complete planner stays atomic to keep day partitions and accommodation references consistent. The active traveller and navigation/comparison preferences remain device-local.

Every envelope contains exactly `id`, `kind`, `payload`, `deleted`, `updatedAt`, `writer`. IDs and author strings are 1–128 characters; author must equal `request.auth.uid`. `updatedAt` is a nonnegative integer, no more than five minutes ahead of request time, and cannot decrease on an update. `deleted` is a boolean. Hard deletes are denied.

- Place payload: a map with exactly `placeId`, `stances`, `carriedOver`; placeId must match the document ID. At most two stances, each with exactly a nonempty bounded `travellerId` and one of `interested` / `not-interested`. Duplicate profile IDs are rejected. An empty stance list requires carriedOver=true.
- Deleted place: retain the envelope, set `deleted:true`, `payload:null` and an updated timestamp. Tombstones are never discarded or hard deleted.
- Roster payload: one or two profiles, each with exactly `id` (1–128 characters) and `label` (1–80 characters). Duplicate profile IDs, extra fields and invalid element types are denied. No roster tombstones.
- Planner payload: a JSON string of 4–250,000 characters, including `null` for no plan. Rules enforce its type/size and envelope, while the app's V8 parser validates JSON syntax, fields and relational integrity. Firestore rules cannot parse JSON or iterate arbitrary nested arrays; planner semantic validation is a client boundary. An authenticated malicious visitor can write a bounded invalid JSON string and stop client sync until repaired. No planner tombstones.

The wire adapter exposes place/roster maps and arrays to rules while retaining JSON strings in the local journal. It also reads legacy JSON-string payloads; new writes use the typed wire shape. Other trips, unknown state documents, root trip metadata and all unrelated paths are denied. The state listener queries only the two permitted document IDs. Firebase console/Admin SDK bypass rules.

## Merge, clock and preservation

Merge by `updatedAt` per document; ties resolve by writer UID, payload and tombstone flag. Initial unshared records have timestamp zero; first publication stamps an absent record with the current time so an empty second device cannot win a zero-time tie. Local edits receive a monotonically increasing timestamp. Transactions read the latest server document and compare before writing; an offline blind-write queue is not used.

**Clock limitation:** `updatedAt` remains an epoch-millisecond device timestamp, not `serverTimestamp()`. The offline journal orders pending edits before they reach Firestore. Merely assigning server timestamps on arrival would let older offline edits become newer than remote edits and would change the merge policy. A safe migration needs a separate pending-edit/base-revision policy and journal migration; it is not a simple timestamp substitution. Clock skew can bias LWW, and clocks more than five minutes ahead can block publishing. Correct device time before editing. Existing future-stamped pending edits may remain blocked until server time catches up or journal metadata is repaired after preserving a backup; reload alone does not restamp them. LWW also loses the older of simultaneous edits to one place (including different personal stances), the roster or the whole planner; there is no conflict-history UI.

Never replace the local list with a remote list: union IDs and merge envelopes. Empty remote, network/auth/permission/quota errors and malformed remote records never clear local data. Only a winning explicit tombstone removes a place. Capture/persist local intentions before sending requests. Before applying remote data, flush and re-read local changes under canonical locks, validate the merged trip, preserve a rotating preimage in `nihon.recovered.before-sync.*`, and use the existing rollback-capable restore writer. Edits made during requests participate in the merge. Stop the session before cleanup so late responses cannot apply data.

First join maps device profile IDs by roster slot; keep the same person order on both devices. If a device lists the same two names as the shared roster in the opposite order, sync is held without publishing or applying anything. A remote change that would remove more than 10 opinions, or more than 30% of the local ones (minimum 3), is held: a preimage is kept and it applies only after explicit confirmation of that exact set. Besides the 5 rotating preimages, the first preimage of each local day is kept for 7 days; a full storage reports its own message and applies nothing. On a first join with different names and local opinions, sync asks «¿Quién eres en este viaje?» and reorders the local profiles so the person holding the device sits in the chosen slot. Held removals can be applied or rejected («No, conservar los nuestros» republishes the local likes as newer updates of the same documents). Removals applied automatically are counted per device over 24 h and the next one is held once the total would pass 10. Pre-sync copies can be restored from Nosotros through the normal import preview and confirmation. **Decision (N4):** a plan emptied on one device is not published, so sync restores the shared plan; an explicit «clear shared plan» action can be added later if wanted. Import remains an explicit, confirmed local replacement; the next sync captures its changes and removal tombstones. The recovery preimages are short-term copies, not historical backups. Local storage failure can prevent rollback; preserved originals remain available.

## Offline and Spark

Local writes and sync metadata survive reloads. Auth creation needs connectivity; an already loaded trip remains usable when Auth or Firestore fails. Firestore SDK retries ordinary connection loss, pending transactions retry on subsequent sync cycles, and auth errors retry every 15 seconds. After changing deployed rules/provider configuration following a terminal listener failure, reload the app to recreate listeners. No durable Firestore shared-device cache is enabled. Anonymous identity can change if browser/Auth storage is cleared; the canonical local trip is not cleared automatically.

Check local edits every two seconds and write only changed records. Two listeners provide place and shared-state updates. A separate Web Lock serializes sync sessions across tabs where supported; canonical local locks stay short. Tombstones consume storage indefinitely. Spark free quota includes 1 GiB storage, 50,000 reads/day, 20,000 writes/day, 20,000 deletes/day and 10 GiB outbound/month for one free database. Reconnects consume reads; membership lookups are no longer needed. Monitor quota; exhaustion must retain local data. No billing upgrade or paid backend is required.
